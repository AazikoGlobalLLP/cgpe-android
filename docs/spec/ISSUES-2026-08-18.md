## Phase 53 — [m]+[api] Task mismatch: claimed tickets don't become my tasks; reopen breaks counts. **Owner #1.**

**Verified — TWO independent causes:**
- **(a) Claimed ticket never becomes a task — BACKEND gap.** "I'll handle this" (`tickets/[id].tsx:227`) →
  `updateTicket(id,{assignedTo})` → `PUT /api/tickets/:id` writes `assignedTo/ownerName` on the **tickets** doc
  only (`routes/tickets.js:346-352`, **zero** `team_tasks` refs). But Home/Tasks read `getTasks()` →
  `GET /team/task-overview` which aggregates **only** `team_tasks` (`routes/team.js:29`). `team_tasks` rows are
  created only by `POST /api/tasks` (`routes/tasks.js:236`, which mirrors) and admin/leader `POST /team/tasks`.
  So a claimed ticket **can never** appear in the task list.
- **(b) Reopen destabilises counts — MOBILE derivation bug.** `adaptTeamTask` sets
  `dueDate = due_at||dueAt||updated_at||created_at` (`api.ts:306`); an undated task follows `updatedAt`, and the
  backend bumps `updatedAt` on every status change → complete→reopen re-buckets it into today/overdue by
  touch-time. Also the "today" denominator counts done tasks (`todayAll = dueToday ∪ (done && !upcoming)`,
  `tasks.tsx:214`, `home.tsx:1107`), so reopening shrinks numerator **and** denominator → the count animates wrong.
  (The optimistic reopen + rollback + enum mapping are all **correct** — ruled out.)

**Fix:** (a) **[api]** in `PUT /api/tickets/:id`, when it gains an owner, **mirror a row into `team_tasks`**
(`assigneeName = full_name`, `title`, a real `dueAt`, `status:'open'`, `source:'ticket'`, stable `taskId` off the
ticket id; delete/close on unassign) — mirror the existing `routes/tasks.js:225-258` pattern. (b) **[m]** stop
falling back to `updated_at` for `dueDate` (use a stable no-date bucket or `created_at`); make the "today"
denominator schedule-based / `completedAt`-based and identical in `tasks.tsx` + `home.tsx`. Scope **both** · effort **M**.
**Open Q:** mirror only actively-claimed or all assigned? ticket-task `dueAt` from SLA/priority or none? is "today's
progress" meant to include done-overdue, or strictly due-today + completed-today?

## Phase 54 — [api] Team-home leads pipeline: "This lead could not be opened" (403). **Quick, high-impact.**

**Verified — backend scope asymmetry (the leader-tier trap, CLAUDE.md danger zone).** The pipeline is fed by
`getLeads()` → `GET /leads?scope=all` (`api.ts:877`); ids are the real `Lead._id` (`adapt.ts:255`) and the rows are
real leads. `GET /api/leads` (**list**) returns, for a leader, self+team leads, and for anyone the ~9k **unowned firm
leads** too (`scope.js:88-133`). But `GET /api/leads/:id` (**detail**) does a strict self-check —
`lead.advisor_id !== user.user_id && role ∉ {admin,super_admin}` → **403** (`routes/leads.js:266`) — which 403s
exactly the teammate + firm leads the list showed. `getLead` swallows the 403 → `unavailable()` → empty →
`lead/[id].tsx` renders "could not be opened." `tierOf()` folds `leader` into admin **client-side**, but the backend
gates on the real `Profile.role`, and `leader ∉ {admin,super_admin}`.

**Fix:** **[api] only** — make `GET /api/leads/:id` authorize with the **same `visibilityScope`/`canSee`**
(`utils/scope.js:223`) the list uses (both already exported); apply the same to `PUT /:id` (`:455`) for parity.
Genuinely-private leads outside scope still 403; nothing leaks. **Mobile = zero change** (the `Lead` type carries no
`advisor_id`, so the app cannot self-filter). Scope **backend** · effort **S**. Also corrects a **stale comment** at
`api.ts:908` (it claims `PUT /leads/:id` has no ownership check — it does, `leads.js:455`). **Open Q:** widen PUT
(leader can advance a teammate's stage) or keep writes owner/admin-only?

## Phase 55 — [m] Network resilience: the "app doesn't work on my WiFi / this phone" complaint. **High impact.**

**Verified — app-side defects (not purely environmental).** Every read AND `login()` goes through `req()`
(`api.ts:155`) whose only resilience is one `AbortController` at **`REQUEST_TIMEOUT = 4500`** (`config.ts:65`).
(1) **4.5 s is too aggressive** — a cold TLS handshake on a weak cell/loaded WiFi can eat 2–5 s; Home fans out ~6
parallel calls; login uses the same 4.5 s, so a slow network **can't even sign in**. (2) **Zero retry** — one dropped
SYN / handshake stall permanently fails the call ("retry" in `api.ts` is only a tracker-delivery label). (3) **No
error-kind** — timeout vs DNS vs TLS all collapse to one generic failure (`health.ts:80`). Single host, no fallback,
no in-app self-test (backend has an unauth `GET /api/health` 200). `uploadFile` (`api.ts:2698`) has **no**
AbortController → hangs forever on a stall.

**Fix:** **[m] only** — raise `REQUEST_TIMEOUT` to ~12–15 s (reads) + equal/longer for login; add a **bounded
retry+backoff** inside `req()` for thrown/5xx/429/503 (NOT 4xx, NOT non-idempotent writes/uploads); distinguish
AbortError vs TypeError and carry a `kind` into `health.ts`; add a **"Test connection"** that pings `/health`; give
`uploadFile` an AbortController. Scope **mobile** · effort **M**. **Honest:** DNS-can't-resolve / captive-portal /
firewall-blocked-`cgpe.in` remain **network-side** — confirmed by opening `https://cgpe.in/internal/api/health` in the
phone browser on that network. **Open Q:** does `cgpe.in` publish AAAA / are the failing networks IPv6-only/NAT64
(needs a DNS check, not source)? p95 first-byte on those networks to pick the exact timeout?

## Phase 56 — [m] iOS enablement. **Owner priority (iOS mandatory). Gated on an Apple Developer account.**

**Verified.** The app **is buildable for iOS but has never been built.** `app.json` already has `ios.bundleIdentifier
= com.cgpe.connect`, and the Info.plist permission strings are injected by config plugins (`expo-location`
`NSLocation*`+`UIBackgroundModes:[location]`, `expo-local-authentication` `NSFaceID*`). What's **missing** is purely
`eas.json` (no `ios` build profile) + an **Apple Developer Program account ($99/yr — hard external prerequisite**; EAS
is logged into an Expo account only, iOS signing needs Apple credentials). Native pieces: `expo-intent-launcher`
(battery-opt) is Android-only but every call is `Platform.OS==='android'`-guarded → degrades cleanly; Face ID
(`biometricIdentity.ts`), the WKWebView map, sensors, and all data screens **work fully on iOS.**

**HONEST 24/7 CONFIRMATION (owner asked):** iOS is a **first-class app** for login / data / map / Face ID, and it
**records routes while on-duty with the app alive or backgrounded** ('Always' permission, blue indicator). It **cannot**
match Android's always-on tracker: after a **force-quit** continuous updates stop, after a **reboot** recording stays
off until the app is reopened once, and the watchdog is opportunistic (BGTaskScheduler, not the ~15-min WorkManager
cadence). `tracker.ts` is architected around Android's foreground service (`:458-467`) which iOS ignores. So: **yes,
make it reliable for iOS for everything except the guaranteed-24/7-after-force-quit-or-reboot feature, which is an
Android-only capability — do not promise iOS parity on that one.**

**Fix:** add an `ios` profile to `eas.json` (TestFlight via `production` + `submit.production.ios`, recommended, or
ad-hoc via `preview` needing each iPhone UDID); `app.json` add `ios.infoPlist.ITSAppUsesNonExemptEncryption:false`;
let EAS manage credentials; `eas build -p ios`; verify Face ID / map / on-duty background route on a physical iPhone;
rewrite the tracker/Phase-41 docs to state the honest iOS limits. Scope **mobile** (gated on the Apple account) ·
effort **L**. **Open Q (owner):** buy the Apple Developer membership? TestFlight vs ad-hoc? accept the honest iOS 24/7
limit, or invest in the coarse mitigations (significant-location-change + region monitoring, optionally APNs silent-push
which touches the backend)?

## Phase 58 — createdAt/updatedAt "" — **premise NOT reproduced; needs one concrete example.**

**Verified — the app does NOT store `""` for created records.** Optimistic local copies stamp real
`new Date().toISOString()` (`api.ts:964/576/1206`); create POST bodies **omit** `createdAt/updatedAt` so the **server**
stamps them (Mongoose `timestamps` on every model). The only `''` are **read-path sub-field fallbacks** in
`adapt.ts` (a note's `at`, a timeline `at`, a thread `lastAt`, a WA msg `at`, a reminder `date`, a notif `at`) shown
only when the server omits that sub-field, never written back. The one literal `createdAt:''` is a test fixture.
**So this is not a create-path bug.** If the owner sees a blank time, it's either a server-omitted sub-field on a
specific screen (fix = a display placeholder like `home.tsx:1634` already does, or the backend returns the field) or a
`''` written by a **non-app** writer (import script / n8n / admin panel). **Action:** owner names the exact
screen+record; do **not** fabricate a server timestamp client-side. Scope **needs owner repro** · effort **S**.
