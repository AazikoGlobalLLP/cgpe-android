## ⚠️ SYSTEMIC ROOT CAUSE FIRST — the prod backend is many phases behind the code

**This one fact explains several of the "server did not answer / could not be reached" symptoms below.**
The backend deploy pipeline (`cgpe-backend-main/.github/workflows/deploy.yml`) deploys **only `origin/main`**.
Live `origin/main` is at **Phase 38–40** (`1cad312`), but every "shipped" backend piece the owner has
been told is done — Phases 41–68: `task-report` (perf), `break-locations` (orange pins), dual-office
geofence, clock-in reason, commissions target/byProduct, the **ticket→team_tasks mirror** — lives on the
`shivam` branch / local `main` and has **never been merged to `origin/main`**, so the pipeline never
deployed it. **"Backend done" has repeatedly meant *done in code*, not *live on the server the app talks
to.*** (Caveat: if the backend is instead deployed manually rather than via the Action, the same
conclusion holds — the endpoints simply aren't answering on the running server.)

**CONCRETE PROOF (verified 2026-08-19).** The ticket→task mirror the owner reported as *still* not
working (Phase 69 below) is commit **`cb3f9de`** ("Phase 68 — claimed/assigned ticket mirrors into
team_tasks"). `git branch -r --contains cb3f9de` returns **nothing** — it is a **local-only commit,
never pushed to any remote**, and `origin/main` (`1cad312`) does not contain `syncTicketTaskMirror` at
all. So the "done" backend work is not merely un-deployed, some of it is **un-pushed**.

**OWNER ACTION (blocks Phases 64, 66, 68, 69 and the whole "shipped-but-not-live" backlog):** have the
backend team **push their work, merge the vetted branch into `origin/main`, and deploy + restart
`:3001`**, then verify a couple of endpoints answer live (see §68). The mobile session **cannot** do
this — our `git push` is 403-blocked. Until this happens, mobile code that consumes those endpoints is
correct but shows honest "could not load" (or, for tickets, "nothing happens") on the phone.

## Phase 63 — [m]+[api]+OPS Background location: capture a real point every ~60 s and RETAIN every point (the "Pavitra" case). **Owner's #1 concern.**

**Symptom.** A member ("Pavitra") had the app open + clocked in for ~20 h, yet her exact location never
came through, only ~8 km was counted, and it drew one continuous **straight line**.

**Verified — three stacked causes:**
1. **The route is recorded at `Balanced` (~100 m) accuracy, and the backend SILENTLY DROPS every shift
   point with accuracy > 100 m.** App requests `Location.Accuracy.Balanced` (`src/lib/tracker.ts:394`,
   both motion profiles `motion.ts:51-69`); backend `routes/timeTracker.js:1671` = `p.accuracy <= 100`
   filter, returns 200 with `added:0`, and the app clears its buffer on a 200 (`tracker.ts:619`,
   `api.ts:2320`) → coarse fixes are gone for good. The two numbers collide, so most real fixes are
   discarded. **(APP config + BACKEND.)** (The off-duty/ambient path deliberately does NOT drop coarse
   fixes — `timeTracker.js:1778` — so the *clocked-in* recorder is the strict one, the inverse of what
   the owner wants.)
2. **A stationary phone records NOTHING.** `distanceInterval: 30` (`motion.ts:52`) means a point is only
   logged when she moves ≥ 30 m — not "every 60 s at whatever point she is." And when the accelerometer
   classifier reads "still", the interval stretches to **5 minutes** (`STILL_PROFILE.timeInterval:
   300000`, `motion.ts:65`). **(APP config.)**
3. **The 8 km straight line = the background service was probably not running for most of the 20 h** — a
   start point, an end point, nothing between (`_layout.tsx:11-17` warns of exactly this). Most likely
   her **installed APK predates the Phase-41 background modules** (native → NOT OTA; the team diagnosed
   this same class on 2026-08-17, `PHASES.md:1444`) or her **OEM battery-killer Doze-killed it**. The
   whole Phase-41 stack is **built but DEVICE-UNVERIFIED**. **(OPS / native build — needs the device +
   a DB check to confirm.)**

**Fix.**
- **[m] `src/lib/motion.ts` (JS-only, but ships in a build):** `MOVING_PROFILE.distanceInterval 30 → 0`
  (record on the time interval even when still — the single most important change for "every point");
  add a `'high'` accuracy case (`tracker.ts:394`) and set the moving profile to it (real sub-100 m
  fixes that survive the filter — battery tradeoff to confirm); neutralise the STILL 5-min stretch
  (`timeInterval 300000 → 60000` or disable motion adaptivity) so cadence stays ~60 s; optionally raise
  `MAX_POINTS` (`tracker.ts:115`, ~4 h buffer) for long dead-zone shifts.
- **[api]** relax/remove the `accuracy <= 100` **shift-path** drop (`timeTracker.js:1671`) — raise to
  ~500–1000 m or match the ambient path which keeps coarse fixes; keep returning `dropped` for
  observability. Needs a deploy + `:3001` restart.
- **OPS (do FIRST, free):** confirm which **APK build** Pavitra has (if < v1.9.0 `86c1406c`, background
  recording never ran — reinstall current APK); set her phone Location = **Allow all the time**, Battery
  = **Unrestricted**, OEM **Auto-start ON**; and **query her tracks session in the DB** (`point_count`,
  `distance_m`, `last_point_at`, server `dropped` count) — this is the definitive disambiguator between
  "filter dropped them" and "service never ran."
- **Honest ceiling:** even done perfectly, guaranteed-every-60-s-24/7 is **not fully achievable** on
  aggressive-OEM Android — the foreground service + 15-min watchdog floor (`tracker.ts:66`) means up to
  ~15-min gaps after a kill. Scope **[m]+[api]+OPS · L** (needs a native APK build to ship + device
  verification). **Open Q (owner):** accept the battery cost of `High` accuracy + 60 s always-on?

## Phase 64 — [api]+[m]+OPS Monitor "Live field status 0" and "On duty 0" (staff ARE clocked in), and the map "server did not answer" banner.

**Verified — TWO separate causes (a restart alone will NOT fix the zeros):**
- **(a) "On duty 0 / Live field status 0" — a real BACKEND bug.** `getAgentLocations`
  (`api.ts:2588`) fans out to `/attendance/user/:id` and needs clock-in coordinates (`toPin`
  rejects a row with no `clock_in.lat/lng`, `api.ts:2577`). But `routes/attendance.js`
  `dayLogToAttendanceRecords` (`:38-57`) maps the daylog and **drops the coordinates** — it copies
  `clock_in.time` but not `s.clockInLoc.{lat,lng,city}` (which DOES exist, `models/DayLog.js:58`,
  written at `timeTracker.js:520`). So `getAgentLocations` returns `[]` for everyone **even on a
  perfectly healthy server**; `getTeam` derives `clockedIn` from those (empty) pins (`api.ts:1802`), so
  On-duty is 0 too. **One backend fix resolves both.**
- **(b) Map "server did not answer" — OPS + a minor APP over-report.** That copy is the global
  `health.degraded` flag (`agent-map.tsx:250`, `health.ts:80`), which needs a real 5xx/timeout/404.
  Most likely trigger: `getBreakLocations` treats a **404** (endpoint not on the running build) as an
  outage — it suppresses only 403 (`api.ts:2662`) and routes 404/5xx through `unavailable()`→banner,
  unlike the standard `reportIfOutage` which treats 404/501 as a quiet answer (`health.ts:131`). Given
  the deploy gap (§top), break-locations 404s on prod → banner.

**Fix.** **[api]** in `dayLogToAttendanceRecords` (`attendance.js:38-57`) add `lat`/`lng`/`city` from
`s.clockInLoc`/`s.clockOutLoc` into the mapped `clock_in`/`clock_out` (~5 lines) — the smallest fix for
(a). **[m]** (optional hardening) route 404/501 through the suppressed path in `getBreakLocations`
(`api.ts:2662`) so an undeployed endpoint is a quiet answer, not a red banner. **OPS** deploy + restart
clears the banner. Scope **[api]+[m]+OPS · S–M**. **Note:** fixing the banner (restart) will NOT fix the
zeros — those need the coordinate fix.

## Phase 65 — [api]+[m] Every team member must appear in agent-locations (not only after they "open the app").

**Verified — a real design gap.** The monitor/map roster's universe of people = `/team/task-overview`
`members[]`, which is built by grouping **`team_tasks` by assignee name** (`routes/team.js:128-134`) —
the full staff directory is loaded but used only to enrich task rows. **A staff member with zero
assigned team-tasks never enters the list** (both `getTeam` `api.ts:1798` and `getAgentLocations`
`api.ts:2606` inherit this; the `/profiles` fallback `api.ts:1834` only fires when task-overview returns
*zero* members, so it never rescues an individual). "Opened the app" is the owner's proxy for "has ≥1
`team_tasks` row" — the true condition.

**Fix.** Source the roster from the **full active-staff directory, LEFT-JOINED** with live location/duty,
so a never-active member shows as *"off duty / no location"* instead of vanishing. **Preferred:** point
the app's roster at `routes/timeTracker.js` `/live-locations` (`:1001`) which already iterates **all**
staff — but first **[api]** must (i) add a `super_admin` gate (it currently leaks every staff
email/role to any caller — see Phase 66 [sec]) and (ii) fix its string-vs-ObjectId `activeSessionId`
compare (`:1020`) that makes `currentLocation` usually null; then **[m]** point `getAgentLocations`/
`getTeam` at it and left-join. Depends on Phase 64(a) for those newly-visible members to ever show a
pin. Scope **[api]+[m] · M**. **Open Q (owner):** show inactive staff greyed as "no location", or only
staff who have EVER shared a location?

## Phase 66 — [api]+[m]+[sec] "Live" button — a master gets member X's current (last-known) location, on or off duty.

**Verified — no on-demand current-location endpoint exists; the honest deliverable is LAST-KNOWN, not a
real-time ping.** `/live-locations` returns only the static **clock-in** coordinate (nothing for
off-duty) and the app never calls it; `/track/sessions` + `/track/:id` are historical replay. There is
**no push infrastructure** anywhere (no FCM/`expo-notifications`/`socket.io-client` — backend
`sendPushNotification` is a stub, `reminderService.js:224`), so a device cannot be woken and asked for a
fresh fix. BUT the last-known read logic already exists internally, unexposed
(`attendanceWatchdog.lastPosition`, `locationGapDetector.newestPointAt`), and off-duty points ARE
collected by the 24/7 tracker (`/track/ambient`) **for members who consented + granted background
permission**.

**Fix.** **[api]** new master-gated `GET /api/time-tracker/last-location?user_id=X` (reuse the internal
readers) → `{ user_id, lat, lng, at, accuracy, off_duty, is_clocked_in, age_seconds }`, `data:null` when
X never shared a point (never fabricate). **[m]** `getLastLocation(userId)` + a **"Live"** button on
`team/[id]` and/or `agent-map.tsx` (gated `canSeeLiveLocation`) → drop one pin + an **honest freshness
label** ("as of 3 min ago / 2 h ago · off duty", or "no recent location"). **[sec]** separately, gate or
delete `/live-locations` (leaks all staff email/role to any authed caller). Scope **[api]+[m] · M**.
**Honest ceiling to state to owner:** "even off-duty" works only where X has 24/7 consent + background
permission; otherwise "Live" shows X's last shift point (possibly days old). A true real-time ping is a
**separate large build** (add FCM + a device-token registry — NOT OTA) and still can't reach an off /
force-stopped / permission-revoked phone.

## Phase 67 — OPS+[m]+[api] Payroll: show ALL employees, and tap one to see their pay breakdown + activity.

**Verified.**
- **(a) Only 1 employee shows / it's "hourly" — OPS/DATA, not a bug.** `buildRoster` builds one row per
  **`payroll_profiles`** document (`routes/payroll.js:325-330`), NOT per staff `Profile`. Only **one
  payroll profile exists**; the other 4–5 staff have logins but no payroll profile, so no row. `/compute`
  is not self-scoped, not paginated, not role-truncated — it returns every profile there is. The "hourly"
  label is that one profile's stored `segment` (`payroll.tsx:44/258`). **Fix = create each employee's
  payroll profile in the admin panel (`POST /payroll/profiles`) and set each `segment`** (`base` for a
  flat ₹40,000, `day_wise`, or `hourly`). The mobile list is **already multi-member** (`payroll.tsx:204`
  maps all rows) — it populates the moment the profiles exist. **No code change for (a).**
- **(b) The owner's real feature — tap an employee → pay breakdown + what they did — APP gap.**
  `MemberRow` (`payroll.tsx:256`) has no `onPress` and there's no detail route. **Build a
  `payroll-detail` screen** for `row.user_id` showing: **(i) the pay breakdown** — reuse
  `earnings.tsx`'s "Pay basis" card + KPI strip + payable-days meter, rendering the server's
  `months[]` inputs verbatim (`working_days`, `present_days`, `worked_hours`, `per_day_rate`, `payable`
  — all already returned by `/compute` `payroll.js:286-297`; **the app renders, never multiplies** —
  rule 2), so "how ₹40,000 was reached" is shown cleanly (base = flat; day_wise = ₹per_day × present of
  working; hourly = ₹rate/h × worked_hours); **(ii) activity** — `getTaskReport(month,{userId})` (Phase
  45) → reuse `performance.tsx`'s `CompletedList` (what they completed, when, on-time). Indian comma
  formatting (`₹40,000`) is **already correct** (`format.ts:25` `inr()`).
- **(c) One small [api] gap:** to show an hourly member's **rate** without the app dividing (rule 2), add
  `hourly_rate` (the engine computes it, `payrollEngine.js:108`, but drops it from `months[]:164-172`) to
  `computeRangeSalary` `months[]`; it flows to both `/compute` and `/my-earnings` via `publicRow`.
  Optional: also add `days`/`sundays`/`holidays` to show the working-days derivation. Additive, tiny.

Scope **OPS (profiles) + [m] (detail screen, M) + [api] (hourly_rate, S).** **Open Q (owner):** what pay
basis (`base`/`day_wise`/`hourly`) for each of the 4–5 employees? Show the working-days derivation line?

## Phase 69 — OPS "I'll handle this" on a ticket STILL does not move it to Tasks (owner re-report 2026-08-19).

**Symptom.** The owner opens a ticket, taps **"I'll handle this"**, and it does **not** appear as a task.
This is the same feature as Phase 53a, which was reported "shipped + verified" — but it does not work on
the real device.

**Verified — OPS deploy/push gap, NOT an app or code bug (hard git evidence).** Claiming a ticket
(`tickets/[id].tsx:227` → `updateTicket(id,{assignedTo})` → `PUT /api/tickets/:id`) is supposed to run
`syncTicketTaskMirror` (backend `routes/tickets.js:366`), which writes one `team_tasks` row so the task
list (`GET /team/task-overview`) shows it. That mirror is commit **`cb3f9de` (Phase 68)** — and it is
**local-only in the backend repo, pushed to no remote, and absent from deployed `origin/main`
(`1cad312`, Phase 38–40)**. So the prod server the app talks to has **no mirror code**: claiming a ticket
updates the ticket's `assignedTo` (that part is in the old build) but never creates the task. The
**mobile side is already correct and tested** — earlier this session we verified the app consumes the
mirror with **zero code change** and pinned it (`api-team-tasks.test.ts`, commit `0b64be8`), and the
follow-up `dueAt = ticket.createdAt` (buckets it Today/Overdue) is also verified in code.

**Fix.** **OPS only** — the backend team must **push commit `cb3f9de` (and the rest of Phases 41–68),
merge to `origin/main`, deploy, and restart `:3001`.** Then, with **no app change**, "I'll handle this"
creates the task and it appears under Today/Overdue. **This is the single clearest proof that the recent
"backend done" items are not live** (see §top). Scope **OPS · trivial once someone with push+deploy
access acts.** **Verify live (owner):** after deploy, claim a ticket → it appears in that assignee's task
list within a refresh.
