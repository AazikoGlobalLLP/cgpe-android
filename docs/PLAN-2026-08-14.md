# Roadmap — owner backlog 2026-08-14 (Phases 34–48)

Scoped from the owner's 2026-08-14 handoff message. **This is a PLAN, not built work.** Each phase below is
still a ≤8-file unit with its own spec written when it is picked up. Ordering is by dependency and value, not
by the order the owner listed them.

**Cross-cutting rules that constrain several of these (do not violate):**
1. **Role by identity = DB `Profile.role`, never a client literal.** The owner's "these 3 phone numbers are
   master" and "keep Viewing-as only for this one number" must NOT become hard-coded phone strings in `src/`.
   `store/roles.ts` `tierOf()` reads `user.role` (Phase 11 deliberately removed the old email literal). The
   phone→master mapping is a **DB data change** (set `Profile.role` for those users) — an owner/`cgpe-api`
   task — and the app keeps gating on role/capability. Same for the one-number Viewing-as exception: it needs
   a capability/flag on that profile, not a literal.
2. **The app never computes money.** Every ₹ is the server's (Phase 16/20/23/25). "Strict salary by
   hours/days" is a **backend payroll-engine formula**; mobile only renders the computed `payable`.
3. **Verify against the real backend before filing or building.** The `[api]` tags in this repo have been
   wrong 5×; grep the sibling `cgpe-backend-main` first, then file a `contracts/INBOX.md` ask only for what is
   genuinely missing. Never invent a field name, endpoint, number, or status value (project `CLAUDE.md`).
4. **Never invent numbers.** "200 m", performance-score weights, salary formula, tracking cadence — read the
   contract / existing code, or lock them with the owner via AskUserQuestion, before writing code.
5. **Security-sensitive items** (biometric account access, 24/7 background location, master-only location
   visibility) must be flagged explicitly and get a security review; 24/7 tracking has DPDP implications.

Legend: **[m]** mobile-only · **[api]** needs `cgpe-api` (file INBOX) · **[db]** owner/data change ·
**[sec]** security-sensitive · **[audit]** investigate-and-report before any build.

## Group A — Audits first (understand before changing; cheap, high value)

### Phase 34 — [audit][m] Self-created task not visible
Owner logged in as `super_admin` (same account as the admin panel), created a task **for himself**, and it did
not appear on the phone even after restart. Investigate the task fetch + visibility path: `getTasks` scope, the
home `my_tasks` widget, `(tabs)/tasks.tsx` filters, and whether an admin/super_admin self-assigned task is
scoped out server-side (assignee vs creator) or filtered client-side. **Deliverable: a written finding** (is it
a client filter, a backend scope, or an assignment-field mismatch?) + the one-line fix, then a small fix phase.
Note the owner also confirmed **admin-panel layout changes DID reach the phone** — so `rbac/app-ui` is wired;
this is specifically a task-data problem. Depends on: nothing. First step: reproduce + grep the task scope in
`cgpe-backend-main`.

### Phase 35 — [audit][m] Intermittent touch-freeze, esp. the AppLock unlock button
Touches stop registering in several places; the clearest repro is the **AppLock** screen — tapping "Unlock"
often does nothing. Investigate `ui/AppLock.tsx` (overlay `pointerEvents`, an opacity-0 View absorbing touches —
the same class of bug the sheet code documents at `sheet.tsx`), the gesture-handler root, and any full-screen
Animated overlay that stays mounted. **Deliverable: root-cause + fix.** Depends on: nothing. Likely `[m]`.

### Phase 36 — [audit][m] Hardcoded-vs-DB data sweep (notifications first, then app-wide)
The owner wants to know how much of the app is **hardcoded/synthesised** vs really from the DB, and the
hardcoded removed. Start with notifications/feeds, then sweep. Note: the project already forbids fabricated data
(`data/mock.ts` is `export {}`; failed reads resolve empty via `unavailable()`), and several screens
**synthesise** legitimately (claim timeline, lead notes, prospects via `pick()`), so the deliverable is an
**inventory** separating (a) real fabrication to remove, (b) documented synthesis to keep, (c) static label maps
(fine). Feeds P37. Depends on: nothing.

## Group D — Location tracking hardening

### Phase 41 — [m]+[api] 24/7 background location, any device, guaranteed capture
Ensure location is tracked **even when the app is closed** and on **any handset (Android/Samsung/iOS)**, and —
per the owner — "24/7." Audit `lib/tracker.ts` (the module-scope background task, `_layout.tsx:18`'s
load-bearing import) + the background-location **permission** request (request "Allow all the time"), the
SecureStore buffer, and delivery to `/time-tracker/track/points`. Confirm the server does not silently drop
points (Phase 7 flagged accuracy > 100 m are dropped). **Flag DPDP/consent + battery**; "24/7" beyond a shift
is a policy decision for the owner. Depends on: nothing (but pairs with 42). **[sec]**. `tracker.ts` has **no
test coverage and is only reachable on a device** (CLAUDE.md).

### Phase 42 — [m]+[api] Route colouring: green inside a shift, red outside
On the location map/replay, draw the path between **clock-in and clock-out green** and any location **outside
that window red**. Needs each track point to carry its clock-in/out session context so the client can segment
the polyline; verify whether `/track/points` already stores the session/in-out boundary (Phase 7 added
`session_id`) or an `[api]` addition is needed. Depends on: 41.

## Group E — Clock-in geofence, per team member

### Phase 43 — [api]+[m] Per-member set location + 200 m clock-in enforcement
Each team member has their **own set location**; clock-in is only allowed within **200 m** of it. Phase 7
already ships a client geofence pre-check and the server is the authority — so the gap is (a) a **per-member
fence** stored/served in the DB (today's fences may be shared/site-based) and (b) server enforcement keyed to
the caller. Mostly `[api]` (per-member fence data + `clock-in` re-validation) with mobile consuming. **Confirm
the 200 m and the accuracy-credit rule** against the contract before coding (Phase 7 noted the server copy says
"0.2 km" and understates by the accuracy credit). Depends on: nothing.

## Group F — Salary & task reports (backend-owned formulas)

### Phase 44 — [api]+[m] Strict salary from working hours / days
Salary must be computed **from actual working hours/days** and shown as one amount. This is a **backend
payroll-engine** change (rule 2 — the app never multiplies). Phase 16 already ships the self-view reading a
server-computed `payable`; Phase 20 the admin roster. The new formula (hours/days → amount) is a `cgpe-api`
product decision — file the exact inputs/rounding to them; mobile renders the result. **Do not invent the
formula or a per-day rate.** Depends on: attendance/day-logs being reliable (already live).

### Phase 45 — [api]+[m] Completed-tasks report + performance score
A per-member report of **what they completed, when, and how much**, with a **performance score**. Hard rule from
the owner: **count only tasks that were assigned AND actually completed** — **not reminders**, not
self-created-but-unfinished. Needs a backend aggregate (completed-assigned tasks per member + a score) — file
the shape + the score definition to `cgpe-api`; **do not invent the score weights** (lock with owner). Mobile
renders it (feeds the master surface, Phase 39). Depends on: 34 (task-scope clarity helps define "assigned").

## Group H — Security-sensitive, spec carefully, do last

### Phase 48 — [sec][m]+[api] Biometric (fingerprint/face) session restore after logout
Scenario: user logs in, closes the app, returns 2 days later logged-out, and should be able to get back into
**their own account** with **fingerprint/face only** — no id/password/OTP. Interpret "khud ka account create ho
jana chahiye" as **restore the existing sealed session**, not literally mint a new account — **confirm with the
owner.** `lib/biometricIdentity.ts` already seals `(userId, token)` behind SecureStore biometric, but **only the
WRITE half is wired** (PROJECT_MAP §lib) — this phase wires the READ/unlock half + a token-refresh path with
`cgpe-api` if the stored token has expired after 2 days. **Requires a security review** (a biometric that
restores a bearer token is an auth surface). Depends on: token-refresh support. Do last.
